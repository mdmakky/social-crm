# Contacts slice: adversarial security review

Scope: schema `crm.ts`, migrations 0004-0007, `crm-rls.test.ts`, `core/contacts.ts`, `contracts/crm.ts`, API routes (contacts, crm-config, imports, scope, workspaces), `crm-service.ts`, `app.ts`.
Method: code read, live Postgres inspection (crm DB, role `crm_app`), reproduction scripts under `/tmp/claude-1000/rv/` (nothing written to the repo except this file). Existing suites pass: api contacts/list/config/imports 78/78, db crm-rls 17/17.
Reproduction scripts (run with Node 24: `node --experimental-transform-types --no-warnings <script>`):
`/tmp/claude-1000/rv/redos.mjs` (pure core), `api1.mjs` (isolation, roles, cursor), `rls.mjs` (raw SQL as `crm_app`), `api2.mjs` (imports, races, logs). Raw outputs: `out1.txt`..`out3.txt` in the same dir.

Counts: blocker 1, major 4, minor 10.

---

## Findings

### B1. blocker: ReDoS in `normalizeEmail` freezes the whole API from one import request
- Files: `packages/core/src/contacts.ts:6-9` (regex runs before the length check), reached via `buildContactFromRow` (`contacts.ts:179-181`) from `routes/imports.ts:35` (preview and commit). Upload accepts cells up to 5M chars (`contracts/crm.ts:142`).
- Regex `^[^\s@]+@[^\s@]+\.[^\s@]+$` is quadratic on input like `x@.a.a.a...@` (fails at the end, backtracks at every dot).
- Repro: `node ... redos.mjs`: 10k chars 104 ms, 20k 318 ms, 40k 1.3 s, 80k 4.9 s (clean quadratic). API level (`api2.mjs` step 9): a 40 KB email cell made `/imports/:id/preview` block the event loop for 954 ms. A 1M char cell is roughly 13 minutes; 5M chars is hours. Node is single threaded, so every tenant is down for the duration, and the request cannot be cancelled.
- Who can trigger: any registered user. `POST /v1/workspaces` is open and makes the caller owner, who holds `data.import`. No rate limit.
- Fix: check `s.length <= 254` before the regex (reject early), and use a linear pattern, for example `^[^\s@]{1,64}@[^\s@.]+(\.[^\s@.]+)+$` after the length gate. Add a per-cell cap (for example 1000 chars) in `parseCsv`. Add a regression test with a 100k char cell asserting under 50 ms.

### M1. major: no request size limit, no rate limit, no quota on imports (memory, CPU, storage DoS)
- `apps/api/src/app.ts` and `server.ts` have no `bodyLimit`, no timeouts, no throttle for CRM routes (grep confirms: no `bodyLimit|statement_timeout|rateLimit|onError` anywhere in `apps/api/src`).
- The 5 MB cap is enforced three weak ways: (a) zod `.max(5*1024*1024)` counts UTF-16 chars, after `c.req.json()` has already buffered and parsed the whole body (`routes/scope.ts:20`); a `€` is 3 bytes so about 15 MB of body passes, and the 40 MB test body was fully read then answered 400, not 413 (`api2.mjs` step 7); (b) `parseCsv` (`core/contacts.ts:96`) checks `text.length`; (c) the 5000 row and 50 column limits run after `csv-parse` has materialised every record: a 5 MB file of `a\n` makes 2.6M records, 1.9 s and +677 MB RSS before rejection; one row of 5M commas costs 3.1 s and +249 MB (`redos.mjs`).
- `import_jobs.csv` is stored per upload with no per-workspace count/size cap and is never deleted (see m3), so storage grows without bound.
- Commit runs about 6 queries per row inside one transaction, up to 5000 rows, holding 1 of 10 pooled connections (`packages/db/src/index.ts:12`). Ten concurrent commits starve the pool for auth and every other route.
- Fix: Hono `bodyLimit({ maxSize: 6MB })` on `/v1` (returns 413 before buffering); count bytes (`Buffer.byteLength`) not chars; pass `to_line`/`max_record_size` and `columns` limits to `csv-parse` so it aborts early; per-user and per-workspace rate limit on `POST /imports*` (reuse `WindowCounter`); cap open (uncommitted) jobs per workspace (for example 5) with a TTL purge; set `statement_timeout`/`idle_in_transaction_session_timeout` for `crm_app`.

### M2. major: unhandled DB errors give 500 and log full SQL parameters (PII, whole CSV)
- No `app.onError`. Hono's default logs the thrown `DrizzleQueryError`, whose message contains the query and every bound parameter.
- Repro (`api2.mjs`, `out3.txt`): `POST /contacts` with `name:"Zed\u0000Pii", email:"pii-secret@example.com"` returns 500 and the log prints `params: ...,Zed Pii,pii-secret@example.com,...,<creator user id>`. `POST /imports` with a NUL byte returns 500 and logs the entire CSV as a bound param (up to 5 MB per log line). Imports commit has a try/catch (`routes/imports.ts:179-181`) but logs `e.message`, which carries the same `params:` text, so a failed commit logs contact rows.
- Other attacker-reachable 500s found (`api1.mjs`): crafted cursor `{"k":"garbage","id":<uuid>,"sort":"lastActivity","dir":"desc"}` (`routes/contacts.ts:49-56,75`, `k` only checked as string, then cast `::timestamptz`); `createdTo=9999-12-31` (adds a day, `toISOString` gives year 10000, Postgres rejects, `contacts.ts:42-43`); `createdFrom=+275760-09-13`. Each is a 500 plus an SQL/params log line. None leaks to the client (body is plain "Internal Server Error"), so this is log hygiene and availability noise, not a data leak.
- Fix: `app.onError` that logs only `requestId`, error class and `code`/`constraint` (never `message`, `params`, `query`) and returns a JSON 500 with the request id; strip `\u0000` in zod (`.refine(s => !s.includes("\0"))`) or in `body()` and in `parseCsv`; validate cursor `k` with a timestamp regex and `createdFrom/To` with a year range 1900-2100; replace `console.error(..., e.message)` in imports with the safe logger.

### M3. major: import "update" silently replaces the real name with the email address
- `core/contacts.ts:186` sets `name = get("name") || first+last || email || ""`; `routes/imports.ts:156` then does `name: k.name || cur.name`, and `k.name` is the email when the file has no name column.
- Repro (`api2.mjs` step 3): contact "Real Name" / real@example.com; import CSV `email,company` with `onDuplicate:"update"` returns `updated:1`; contact name afterwards is `real@example.com`. Same for phone-only files (name becomes the phone). Data loss with no warning in the preview.
- Fix: carry a `nameWasDerived` flag from `buildContactFromRow` (true when name came from email/phone) and skip `name` on update when set; add a test.

### M4. major: DB policies for `workspaces`, `memberships`, `audit_log` rely on the GUC alone; the DB does not back the matrix there
- Live policies (`pg_policies`): `audit_log_select/insert` = `workspace_id = app_workspace_id()` only (no role check); `workspaces_update` = `id = app_workspace_id()`; `memberships_select` = `user_id = app_user_id() OR workspace_id = app_workspace_id()`; `workspaces_select` includes `id = app_workspace_id()`.
- The scoped middleware (`routes/workspaces.ts:66-73`) sets `app.workspace_id` to the URL id before membership is proven, so any non-member's transaction in that window has the target tenant's GUC. Repro (`rls.mjs`, as `crm_app`, user = owner of A, GUC workspace = B, not a member of B): reading B's memberships, B's audit_log and B's workspace row each returned 1 row; inserting a forged `audit_log` row for B succeeded; a viewer of A could `UPDATE workspaces SET name=...` (rolled back). All 10 contact-slice tables correctly returned 0 rows in the same situation, so there is no live leak today: it depends on the API never running a query in that window beyond `roleIn`.
- Impact: any future bug in the middleware (or one SQL injection) exposes cross-tenant audit logs and memberships and allows audit forgery. Matrix says `audit.view` and `workspace.settings` are admin only; the DB allows viewer.
- Fix: new migration: `audit_log_select USING (workspace_id = (SELECT app_workspace_id()) AND (SELECT app_has_role(array['owner','admin'])))`, insert limited to active members (`app_has_role(all roles)`), `workspaces_update` add `app_has_role(array['owner','admin'])`, drop the bare `workspace_id = app_workspace_id()` branch of `memberships_select` for non-members. Alternatively set the GUC only after `roleIn` succeeds (run `roleIn` with only `app.user_id`).

## Minor findings

- m1. DB does not back several API-only rules (`rls.mjs`, all rolled back): an agent can soft-delete a contact (`UPDATE contacts SET deleted_at`; matrix `contact.delete` is admin only, API blocks at `contacts.ts:245`, policy `contacts_update` allows agents); an agent can delete or update another user's task (`tasks_update/delete` allow all agents, API `task.edit` is own-only at `contacts.ts:415`); `activities_insert` does not require `actor_user_id = app_user_id()`, so an agent could insert a forged `contact.deleted` activity attributed to the owner; `contacts.owner_user_id`, `tasks.assignee_user_id`, `notes.author_user_id` are FK to `user`, not to `memberships`, so the DB accepts a non-member owner (`UPDATE ... owner_user_id=<other tenant user>` succeeded). Export restriction (`data.export`) cannot be a DB rule because export is a plain SELECT. Fix: `contacts_update WITH CHECK (deleted_at IS NULL OR app_has_role(owner,admin))` and a `USING` guard for un-delete; own-or-admin predicate on tasks; `actor_user_id = app_user_id()` in `activities_insert`; composite FK `(workspace_id, owner_user_id) -> memberships(workspace_id,user_id)`.
- m2. Duplicates are advisory only and racy. `POST /contacts` is check-then-insert with no unique index: 5 concurrent identical posts gave `201,201,201,201,409` and 4 rows (`api2.mjs` step 5). Import vs manual create races the same way. `allowDuplicate` is a product feature, so a unique index is not possible; document it, or take `pg_advisory_xact_lock(hashtext(workspace||email))` around check+insert.
- m3. Raw CSV retained forever. `import_jobs.csv` (full PII) stays after commit (`api2.mjs` step 8: `committed:4790` bytes still stored); no cleanup job, no DELETE grant, abandoned `uploaded` jobs also stay. Readable only by owner/admin via RLS and no route returns it, which is good. Fix: after commit set `csv = ''` (UPDATE is allowed) and purge uploaded jobs older than 24 h with a scheduled job.
- m4. Import skips contract limits: `name`, `company`, `phone` have no length cap in `buildContactFromRow` (API caps 120/120/40). A 1 MB name is stored. Also `phone` stores the raw string, which may be huge but whitespace padded (`normalizePhone` accepts any amount of spaces). Fix: reuse the zod field caps in the row builder.
- m5. Import `update` with a missing target falls through to create. `routes/imports.ts:150-165`: when `pr.action==="update"` but no `createdByKey` hit (an in-file duplicate whose earlier row was skipped or updated, matched on a key the existing contact lacks), the `else` branch inserts a new contact, creating a duplicate. Also a row matching contact X by email and contact Y by phone merges into X only and writes Y's phone onto X. Also update ignores `validateCustomValues` failure silently (`check.ok ? ... : cur.custom`), dropping custom values without telling the admin. Fix: treat missing target as skip with a counted warning; surface custom failures in the preview.
- m6. Formula-injection guard is sound but lossy. Verified (`redos.mjs`): `'=cmd` exports as `'=cmd`, `\t=cmd` exports as `'\t=cmd`, `=cmd` exports as `'=cmd`; importing `'=cmd`, `\t=cmd`, `=cmd` all store `=cmd` and re-export guarded (`'=cmd`), so no unguarded formula can be smuggled through a round trip (the unguard set `[=+\-@]` is a subset of the guard set `[=+\-@\t\r]`). Side effects: legitimate values beginning with `'` + `= + - @` lose the apostrophe on import, and every phone starting with `+` is exported as `'+1555...` (visible apostrophe in non-Excel consumers). Header cells and custom field labels also pass through `csvCell`. Not exploitable; mention in the export UI or add the guard only for `= @` plus tab/CR/LF and write phones as text differently. Also add `\n` to the guard set (OWASP lists it).
- m7. Soft-deleted contacts: `noteWrite` and `taskWrite` (`contacts.ts:328-348, 406-432`) never call `loadContact`, so notes and tasks of a deleted contact can still be edited or deleted by id; `recordActivity` also bumps `last_activity_at` on deleted rows. Low impact (same workspace, permission checks still apply). Fix: join on `contacts.deleted_at IS NULL`.
- m8. Read-side side effect: `GET /lifecycle-stages` seeds stages for admins (`crm-config.ts:28`); two concurrent first visits can both insert defaults (no unique on stage name). Move seeding to workspace creation (already done) plus a migration for old workspaces. Related TOCTOU: concurrent `POST /custom-fields`, `/tags`, add-tag-by-name, and the "last active stage" archive check (`crm-config.ts:64`) are check-then-write; unique violations surface as 500 (M2 logging) and two concurrent archives can leave zero active stages. Code-read only, not reproduced.
- m9. Activity timeline keeps PII after deletion: `note.added` stores a 120 char preview of the note in `activities.data` (`contacts.ts:323`) and the table is append-only, so a deleted note's text and a deleted contact's name (`audit_log` summary, `contacts.ts:253`) persist. Conflicts with a future erasure (DSR) flow. Fix: do not store previews, or store a redactable column outside the immutable row.
- m10. Minor hygiene: `x-request-id` is accepted from the client, unbounded (5000 chars echoed, `api2.mjs` step 10) and stored in `audit_log.request_id`; `x-forwarded-for` is trusted for `audit_log.ip` (spoofable unless a proxy overwrites it); `crm_app` can read the whole `user` table (1604 rows in `rls.mjs`, no RLS; inherent to Better Auth but widens any SQL injection); the export resolves owner emails from `user` for ex-members (`contacts.ts:112-113`). Fix: validate `x-request-id` as `^[\w-]{8,64}$`, trust XFF only behind a known proxy, and select export owner emails through `memberships`.

## Checked and found sound (evidence)

Tenant isolation (`rls.mjs`, `api1.mjs`):
- All 10 tenant tables have ENABLE and FORCE RLS (`pg_class.relforcerowsecurity = t` for each; `crm_app` is not owner, not superuser, no BYPASSRLS). SELECT as the owner of A with GUC workspace B (non-member): 0 rows on every one of the 10 tables; with GUC A and `WHERE workspace_id = B`: 0 rows; GUC set but no user: 0 rows.
- Policies per command are correct in 0005 and in the live DB after the 0007 initplan rewrite (same predicates wrapped in `(SELECT ...)`); every `UPDATE` policy has `WITH CHECK`; `app_has_role` requires an active membership for the GUC workspace so `app.workspace_id` alone never grants access on the 10 tables. Functions are not SECURITY DEFINER (`prosecdef=f`), `crm_app` has no CREATE on `public`, cannot disable the trigger ("must be owner") and cannot set `session_replication_role`.
- Cross-tenant writes fail: inserting a contact with workspace B (RLS), moving a contact to B by UPDATE (RLS WITH CHECK), contact with B's stage, contact_tags with B tag or B contact, notes/tasks/activities on B's contact (composite FKs `(workspace_id, id)`), note with forged author (RLS).
- GUC injection: `withContext` binds values via `set_config($1,$2,true)` (transaction local, parameterised), `workspaceId` is UUID-validated, `userId` comes from the session. Role is read in a separate transaction but every statement re-checks RLS.
- Revokes: `crm_app` has no DELETE/TRUNCATE on lifecycle_stages, contacts, custom_field_definitions, notes, import_jobs and no UPDATE/DELETE/TRUNCATE on activities (`information_schema.role_table_grants`); `contact_tags` has no UPDATE policy.
- Append-only trigger: `BEFORE UPDATE OR DELETE OR TRUNCATE ... FOR EACH STATEMENT` fires even on `WHERE false`; `crm_app` is stopped by privilege first; the owner and the superuser (`UPDATE activities`) hit `activities are append-only`. Only a superuser with `session_replication_role=replica` bypasses it (updated 2141 rows in a rolled back test), and the owner can `DISABLE TRIGGER`; both are admin-level and acceptable, but the test title "including the table owner" overstates it.
- IDOR through the API: contact of B via A's path or B's path: 404; B user patching A's task through B's path: 404; note id with a different contact id: 404; B's stage, tag, non-member owner on create: 400 `invalid_stage/invalid_tag/invalid_owner`; B tag added to A contact: 404. All lookups carry `workspace_id` plus RLS.
- Mass assignment: `{workspaceId, createdBy, version:99, deletedAt, id}` on `POST /contacts` is stripped by zod; row verified in DB: workspace = A, created_by = caller, version 1, deleted_at null. `PATCH` takes `expectedVersion` only as a guard.

Roles (`api1.mjs`):
- viewer: export, import, delete, create contact, create tag, shared view, custom field, audit log all 403; viewer note create 403. agent: export, import, delete, shared view, custom field, audit 403; agent editing the owner's task or note 403; agent create contact/tag 201 (matrix allows). Export/import are `data.export`/`data.import` = owner/admin only and checked first in the handler. Saved views: personal views RLS-private, shared need `view.share` and DB `user_id IS NULL` admin-only.
- Unauthenticated `/v1/...` 401; non-member 404 (no existence leak); `isUuid` guards every id; mutating requests with a foreign `Origin` are 403.

SQL injection (`api1.mjs`, code): every user value in `filters()` and `page()` is a bound parameter; the only `sql.raw` inputs are `SORT_EXPR[sort]`, `TS(...)`, and `<`/`>` chosen from fixed maps after zod enum validation (`sort`, `dir`); the cursor is bound as `$n` text/`::timestamptz`/`::uuid` and must match `sort`/`dir`. Probes: cursor `k = "x') OR 1=1 --"` returns 200 with only A rows, cursor with B's contact id returns A rows only (id is a comparison value), `search=%` matches literally (`escapeLike` + `ESCAPE '\'`, total 0), `search=' OR 1=1--` and `ownerId=x' OR '1'='1` return total 0. `tagIds` are UUID-validated, max 10, and joined with `workspace_id`. Only the cast failures in M2 error out; none read other tenants.

Concurrency:
- `PATCH` with 6 concurrent requests on the same `expectedVersion`: one 200, five 409 (version in the `UPDATE ... WHERE version`, atomic).
- Import commit of one job by 3 concurrent callers: one 200 (200 rows), two 409 `already_committed`; no duplicate rows (200 counted). `FOR UPDATE` on the job row works under READ COMMITTED. Import is all-or-nothing in one transaction.

CSV: ReDoS aside, `parseCsv` rejects over 5000 rows or 50 columns, delimiters limited to `, ; \t`; export capped at 10,000 rows (413), audited (`data.exported`), `cache-control: no-store`, fixed filename.

Error exposure: clients only ever get `{error:{code,message}}` or plain "Internal Server Error"; no stack or SQL in responses (stack and SQL appear only in server logs, see M2).
