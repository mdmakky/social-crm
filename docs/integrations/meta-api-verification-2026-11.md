## 2. Conflicts with the plan (`docs/architecture/meta-inbox-plan.md`)

- C1, section 3 (HMAC over raw bytes). Meta says the signature is over an "escaped unicode" version of the payload and that decoded bytes give a different HMAC. Our plan hashes the raw received bytes, which is correct only if Meta's wire body is already the escaped form. Meta's text does not say what the wire body is. The plan is not wrong, but it is unproven for non-ASCII text. Action: first real webhook with non-ASCII text decides it. Until then keep a test with an emoji/accented fixture, never re-serialise JSON before hashing, and do not add a decoded-body fallback without evidence.
- C2, section 3 ("Meta retries on non-2xx and its retry window is long"). Meta documents a 5 second response target, a few immediate retries, a 15 minute alert and automatic unsubscription after 1 hour of failures. The readiness doc says generic webhooks retry about 36 hours; the Messenger/Instagram page does not say that. Our design (store then 200) is fine, but an outage over 1 hour silently stops inbound until resubscribed. Action: add a health check that lists `subscribed_apps` for each Page and resubscribes, and record this in the reconnect flow (section 6). The "well under one second" target stays; the hard ceiling is 5 seconds.
- C3, sections 4 and 5 (echo reconciliation by `mid`, "matching text and timing"). Not documented: echo `mid` equals Send API `message_id`. Documented for Messenger: echo carries `app_id` and optional `metadata`. Action for Messenger: send `client_msg_id` in the Send API `metadata` field and reconcile on echo `message.metadata` plus `app_id`, with `mid` as a secondary match. For Instagram there is no documented `app_id` or `metadata` in the echo, so text and timing matching remains the only documented option; keep the human decision step.
- C4, section 3/6 subscription (Instagram `message_echoes`, `message_reads`, `message_deliveries`). These fields do not exist for Instagram. Subscribe Messenger to `messages`, `message_echoes`, `messaging_postbacks`, `message_reads`, `message_deliveries`; subscribe Instagram to `messages` (echo is `is_echo` inside it), `messaging_postbacks`, `messaging_seen`, `message_reactions`. Receipt idempotency by watermark applies to Messenger reads and deliveries; Instagram has `messaging_seen` only.
- C5, section 11 (Graph version to pin). Versions table says v26.0 is latest (expiry TBD) while the debug_token reference shows v27.0. Pin v25.0 or v26.0 in config, confirm v27.0 against the Dashboard, and never use an unversioned call. v20.0 is already expired (2026-09-24) so any example using it is stale.
- C6, section 6 (daily `debug_token`). Works, but needs an app access token (`app_id|app_secret`) or a developer user token, not the Page token itself. The invalidation causes the plan lists (password change, permission removal, app removal, role loss) are only partly backed: 460 password changed and 458 app not installed are documented; the others fall under 463/467 generic text. The plan's wording should say "documented examples" not "complete list".
- C7, section 5.2 ("Send API has no idempotency key; to be reconfirmed"). Still true to the extent of the pages fetched (no mention). Status stays UNVERIFIED-absent; the plan's behaviour (never auto-retry unknown) is the right stance.
- C8, readiness doc (Development mode webhooks). Instagram page says the app "must be published, regardless of app review status, to receive webhooks". The readiness doc and approved decisions assume Development mode. The meaning of "published" here is unclear (it may mean the Page/IG app subscription, not Live mode). This could break the Development-mode-only plan for Instagram. Must be tested first with the real app before building slice 6.

No conflict found with: HUMAN_AGENT off by default (a 7 day tag exists, Instagram needs an optional App Review feature for custom inboxes), one Page = one workspace, 24h window check server-side, error 190 handling, unknown never auto-retried, 10 minute window (an internal setting, Meta documents no relevant delivery time).

## 3. Implementation implications

1. Signature: verify against raw bytes with timing-safe compare; accept `sha256=` prefix only; add non-ASCII fixture; treat Instagram as using the same header only after a real delivery proves it (U1). Log only header class and result.
2. Respond 200 inside 5 seconds always (even for unknown pages, after storing); do not do Graph calls inline.
3. Run a scheduled subscription check per connected Page (`subscribed_apps`) and surface "webhooks disabled" as a reconnect condition.
4. Messenger sends: set `metadata` = our `client_msg_id`; match echo by `metadata`, `app_id` equal to our app id, then `mid`. Store the Send API `message_id` and compare it with the echo `mid` the first time it happens, record the result in `docs/project/testing-report.md`.
5. Error classification table to seed (to be confirmed by real calls): 190 with subcodes 458/459/460/463/464/467 -> `reauth_required`; 10 and 200-299 -> permission failed, token health check; 100 -> invalid parameter (not retried); 551 and 1545041 -> recipient unavailable, `failed`; 4, 17, 613 -> rate limited, treated as definitive "not sent" only if the response was received, otherwise ambiguous; outside-window code unknown, so map by server-side window check first and treat any unmapped 4xx as `failed` with the raw code stored.
6. Rate limits (300/s text, 10/s media per Page) are far above need; implement a per-account queue with a small concurrency cap, and honour 613 with backoff on the next user-initiated send only (never auto-retry unknown).
7. Instagram connect needs a guided check: professional account, linked Page, "Allow Access to Messages" toggle, and `instagram_manage_messages` present in `debug_token` `scopes`. Surface each missing item to the user.
8. Pin Graph version in config; add a test or startup log warning when the pinned version is within 6 months of expiry.
9. Instagram text limit: enforce the stricter of 1,000 bytes in the composer until clarified.
