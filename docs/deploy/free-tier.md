**Status: the DATABASE side is VERIFIED on a real Neon project (2026-11-14); nothing else is deployed.** Render, Vercel and the GitHub workflows are untested. Everything marked UNVERIFIED was not confirmed against the provider's current docs or a real run.

## Verified on real Neon (free plan, PG 18.7, aws-ap-southeast-1)
- Project created without a card through the Vercel Marketplace: `vercel integration add neon --billing-plan free_v3 --name social-crm-db --no-connect --no-env-pull` (the owner's Neon organisation was managed by Vercel, so `neonctl projects create` was refused: `organization is managed by Vercel`). `neonctl projects get` shows `pg_version 18`, plan `free_v3`.
- `scripts/db-bootstrap-roles.mjs`: roles, `pg_trgm`, grants OK. Two findings fixed in the script: (1) `ALTER DEFAULT PRIVILEGES FOR ROLE crm_migrator` needs `GRANT crm_migrator TO CURRENT_USER WITH SET TRUE` first (the Neon owner is not a member of roles it creates); (2) the owner cannot `ALTER ROLE` a role it created, so a re-run now skips a role whose password already works. Re-run is idempotent (all steps `ok`).
- All four roles log in, none is superuser or bypasses RLS. `pnpm --filter @crm/db migrate` as `crm_migrator`: 21 migrations; `uuidv7()` works; 126 policies; 36 tables with forced RLS; the 4 tables without RLS are the Better Auth tables (same as the local database). The app role cannot read `integration_secrets` or `raw_body`; the ingest role can INSERT but not SELECT `webhook_events`.
- API against Neon (local process on another port, real Meta app settings but MOCK-signed fixture): signup, workspace create (RLS + seeding), lists, webhook ingress 200 and bad signature 403 + rejected row, event-driven worker processed the event within seconds (unknown account -> orphan). Request time about 0.4 to 1 s from the test machine to Singapore.
- Direct (unpooled) connection string used; the pooled endpoint was not tested. The connection string carries `channel_binding=require`; node-pg 8 accepts it today and logs an sslmode deprecation warning.
- NOT verified: how much of the free 100 CU-hours a day of use costs; behaviour after the compute scales to zero and wakes; the Neon free-plan limits beyond the pricing page.
 This is a development/demo setup, not production.

## Architecture
| Part | Where | Why |
|---|---|---|
| Web (Next.js) | Vercel Hobby, Root Directory `apps/web` | serverless is fine for the web |
| API + workers | ONE Render free web service (`render.yaml`) | the API also runs the webhook ingress, inbox worker and event dispatcher as timers, which need a long-running process |
| Database | Neon free Postgres | permanent free plan; roles, pg_trgm, PG 18 and all migrations VERIFIED (see above) |
| Wake-up | external free pinger on `GET <api>/health` every 10 min | Render free sleeps after 15 min without inbound traffic |
| Deploys | GitHub Actions on push to `main`: test, migrate, Render deploy hook; Vercel deploys the web by itself | |

Public URLs are `*.onrender.com` and `*.vercel.app`: no domain is bought and the Cloudflare tunnel is no longer needed.

## Process architecture on one Free Web Service (audited 2026-11-14)
Render's Free instance type does not support Background Workers ("Other service types don't support Free instances"), so a separate free worker cannot be deployed. The API process therefore runs the inbox worker, the event dispatcher and the token-check job in-process. Verdict: **a combined process is safe enough for development and demos, and is not a production design on Free.** Findings, from the code and tests:
- **Duplicate worker execution:** only during a deploy's overlap (the old instance keeps serving at least 60 s before SIGTERM, per Render's deploys page). Safe: each webhook event is claimed with `FOR UPDATE SKIP LOCKED`, per-thread advisory lock, `ON CONFLICT DO NOTHING` (tests: concurrent workers on one event give one message; 12 parallel events give one conversation and gapless seq); the dispatcher keeps its offsets in the database (test: two dispatchers never process an event twice); token checks and the 30 day purge are idempotent. Not safe, accepted: the OAuth "pick a Page" selection and the rate-limit counters live in process memory, so a deploy during a Meta login means connecting again.
- **Lost events and notifications:** a webhook is stored before the 200 is sent; notifications are durable domain events with database offsets, reprocessed after a restart (at-least-once, handlers idempotent). The in-memory "event stored" signal is only a hint: the startup pass and the 15 minute fallback recover it. **Real risk, unavoidable on Free:** a webhook that arrives while the service is asleep waits about a minute for the spin-up, longer than Meta's 5 second window; Meta retries a few times and unsubscribes the app after an hour of failures, so a message can be delayed or lost. The pinger reduces this and cannot remove it.
- **Shutdown and restart (fixed in this change):** before, SIGTERM stopped the workers first while the server still accepted requests, a late `tick()` could start a new pass, the database pools were never closed and there was no deadline. Now `apps/api/src/shutdown.ts`: stop accepting, let in-flight requests finish, stop the workers (each waits for its current pass; an event is one transaction, so even a hard kill only rolls it back), end the pools, exit; a 10 second deadline forces the exit (Render sends SIGKILL after 30 s by default, `maxShutdownDelaySeconds`), and a second signal exits at once. Verified: 5 unit tests, a test that a late signal after `stop()` starts nothing, and a real process: SIGTERM with an idle keep-alive connection exits cleanly in about 50 ms.
- **Connection leaks:** the three pools (app, worker, ingest) had a fixed size of 10 and were never closed. `DB_POOL_MAX` now sets the size (`render.yaml`: 5) and the pools end on shutdown. Idle connections close after the driver's 10 s idle timeout, so an idle process holds none (needed for Neon to scale to zero). Worst case in a deploy overlap: 3 pools x 5 x 2 processes = 30 connections; Neon's connection limit for the free plan is UNVERIFIED.
- **Timeouts:** the webhook request is one HMAC check and one INSERT (about 0.4 s measured to Singapore), then 200; no Graph call runs in a request and the worker has its own pool. Render's request timeout limits were NOT FOUND in its docs. `/health` does not touch the database. The server reads `PORT` (Render sets 10000) and listens on all interfaces.
- **Render policy risks:** "Render might restart a Free web service at any time" (handled like a crash) and Render lists invoking external APIs among service-initiated traffic that can get a Free service suspended; whether our Graph API calls count is UNVERIFIED.

## Environment mapping (checked against `apps/api/src/server.ts`)
- `server.ts` requires `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DATABASE_URL_APP`; `WEB_ORIGIN` defaults to localhost and must be set (it is `sync: false` in `render.yaml`). Every `render.yaml` key exists in `server.ts` except `NODE_VERSION`, which is Render's (Render also reads `.nvmrc`; `NODE_VERSION` wins).
- Which URL goes where: `BETTER_AUTH_URL` and `META_PUBLIC_BASE_URL` = the Render URL; `WEB_ORIGIN` = the Vercel URL; `META_OAUTH_REDIRECT_URI` = `https://<vercel url>/v1/integrations/meta/callback`; Meta's webhook callback, data deletion and deauthorize URLs = the Render URL (webhooks must reach the API directly, not through Vercel). The web needs only `API_URL` (= the Render URL) and optionally `NEXT_PUBLIC_NOTIFICATION_POLL_MS`.
- Cookies: the web forwards all cookies to the API, so the session cookie name does not matter to it. Better Auth switches to a `__Secure-` cookie when its base URL is https; that this works end to end through the Vercel rewrite is UNVERIFIED.

## Pipeline ordering
`deploy.yml`: `test`, then `migrate` (needs `test`), then `deploy-api` (needs `migrate`), one run at a time; the Render service has `autoDeploy: false`, so it deploys only through the hook. A failed test or migration stops the chain before any deploy. `ci.yml` no longer also runs on pushes to `main` (it is called by `deploy.yml`). Gaps, accepted and documented: (1) Vercel deploys the web from its own GitHub integration as soon as `main` moves, in parallel and before the migration, so a new web page can call an API route that is not deployed yet for a few minutes (gating the web deploy behind the workflow needs the Vercel CLI and a `VERCEL_TOKEN` secret: not done); (2) the old API keeps running during the overlap against the NEW schema, so every migration must be backwards compatible (add first, remove in a later release).

## Known limits
- **Render free** (page of 2026-11-14): 750 instance hours per month (one always-on service fits: 744 h), spins down after 15 min without inbound traffic, may be restarted at any time, one instance, no persistent disk. A cold start can exceed Meta's 5 second webhook window; Meta retries.
- **Neon free:** 100 CU-hours per month, compute scales to zero after 5 min and cannot be disabled. The API is built not to keep the database awake: the inbox worker is **event driven** (ingress signals it right after it stores a webhook; `INBOX_WORKER_INTERVAL_MS`, 900000 = 15 min, is only a slow safety net), and the notification/event dispatcher polls every second only while the API is being used (any request except `/health` counts for 2 minutes) and every `EVENT_DISPATCH_IDLE_INTERVAL_MS` (default 600000 = 10 min) otherwise; the first request after an idle period wakes it at once. The free pinger hits `/health`, which does not count as activity and does not touch the database. **Not yet measured on Neon:** check the CU-hour usage after a day, and note a 5 to 10 minute periodic query can still keep the compute awake part of the time.
- **Mail:** there is no production mail provider, and `apps/api/src/server.ts` refuses `NODE_ENV=production` for that reason, so the service runs with `NODE_ENV=staging`. Password-reset e-mails are written to local disk on the Render instance and are lost. Pick a provider (decision D22) before real users.
- **Release gates still open:** KMS for the token key (env key only), one API instance only (OAuth pending store and rate limits are in memory), e-mail verification, contact erasure.
- **CI** runs lint, typecheck and unit tests against `postgres:18`. Playwright is not in CI yet. The `postgres:18` service image tag and the action versions (`checkout@v4`, `setup-node@v4`) are UNVERIFIED. 
- Costs: none expected if every limit above holds. Fly.io and Railway are not free (checked 2026-11-14).
- **Single API instance (assumption, checked 2026-11-16):** `render.yaml` sets `numInstances: 1` on the Free plan. Whether Render blocks scaling a Free web service is NOT confirmed by Render docs found (their scaling page names persistent disks as the blocker); the live dashboard setting was not inspected (no API access from here). In-memory limits (WhatsApp connect, imports, password reset) and the OAuth pending store assume one instance. Scaling out needs a Postgres-backed counter first; see `docs/integrations/whatsapp-manual-connect-runbook.md` section 7.

## Attachment storage (Inbox files)
The app never stores binary data in PostgreSQL. Render's free web service has no persistent disk and Neon holds no blobs, so on the free tier a file store must be an S3-compatible bucket (Cloudflare R2, AWS S3, MinIO). Cloudflare R2 has a free tier, but its current terms and limits are UNVERIFIED here; check them before relying on it.
- Without storage configured the app still runs: received media shows as metadata ("storage not configured"), uploads answer `storage_not_configured`, nothing crashes.
- Environment (API service only, never in the web app): `STORAGE_DRIVER=s3`, `S3_ENDPOINT` (for R2 `https://<account>.r2.cloudflarestorage.com`), `S3_REGION` (`auto` for R2), `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (set the last two by hand as secrets; they are never logged or returned). Local development: `STORAGE_DRIVER=local` with `STORAGE_LOCAL_DIR=./.dev-blobs`.
- Optional: `ATTACHMENT_MAX_IMAGE_BYTES`, `ATTACHMENT_MAX_AUDIO_BYTES`, `ATTACHMENT_MAX_VIDEO_BYTES`, `ATTACHMENT_MAX_DOCUMENT_BYTES` (defaults 5, 20, 25, 10 MB) and `ATTACHMENT_ALLOWED_HOSTS` (host suffixes a channel download may come from; default the Meta CDN names, UNVERIFIED).
- The S3 client is our own SigV4 over `fetch` and has only been tested against a fake endpoint: do a manual put, get and delete check against the real bucket before trusting it. Use a private bucket (the API streams files after its own access check; no public or signed URLs are used).
